# 06 — Report a broken daily puzzle, and check the coming days' puzzles

Surface: each AI daily puzzle's screen ("Something wrong with this puzzle?"), a new admin page `/admin/daily-puzzles`
(the next days' puzzles with their answers, reports per day, "Replace"), the data export, erasure. Wave 5. Namespace
`puzzle-reports`. The puzzle screens keep their own look (the daily desk); the admin page is on the site tier.

## User story

As a member who plays the daily puzzles, I want to say when today's puzzle is wrong — two answers fit, the clue
contradicts itself — so that someone fixes it; and as an admin, I want to see tomorrow's puzzles and replace a bad
one before anyone plays it.

## Requirements elicitation

- **What exists (verified):**
  - Five daily modes are generated by a language model (`AI_PUZZLE_MODES` in `lib/daily-puzzles/generate-core.ts`:
    alibi, spectrum, outcast, chainlink, impostor). `getOrCreateDailyPuzzle(mode, dateKey)`
    (`lib/daily-puzzles/generate.server.ts`) validates the model's output (`validateAndNormalize`) and otherwise falls
    back to the deterministic generator (`fallbackPuzzle`), and stores the first result in `DailyPuzzle`
    (`prisma/schema/games.prisma`: `gameMode`, `dateKey`, `source`, `data` including the solution, unique
    `[gameMode, dateKey]`), so "the day is locked to a single puzzle".
  - The prewarm cron (`lib/daily-puzzles/prewarm.server.ts`) writes the coming day's rows at 04:45 UTC, fifteen to
    seventy-five minutes before the America/New_York day starts; nobody looks at them.
  - The public read `GET /api/daily-puzzles/puzzle` (`lib/daily-puzzles/api/daily-puzzles.puzzle.server.ts`) refuses a
    future `date` and caches publicly (`sMaxAge: 3600`). Scores are `DailyPuzzleScore` rows keyed by
    `[userId, gameMode, dateKey]`.
  - Validation is structural; a puzzle can pass and still be wrong. There is no way for a player to say so (no report
    type covers a puzzle) and no admin page for daily puzzles (`app/routes/_site/admin/` has `qotd.tsx` and others, not
    this).
  - The puzzle screens: `components/daily-puzzles/AlibiGame.tsx`, `SpectrumGame.tsx`, `OutcastGame.tsx`,
    `ChainlinkGame.tsx`, `ImpostorGame.tsx`, inside `components/daily-puzzles/PuzzleShell.tsx`.
- **Decisions:**
  - **A puzzle report** is a `DailyPuzzleReport` row (new): `userId`, `gameMode`, `dateKey`, `kind` (`two-answers`,
    `wrong-answer`, `unclear`, `other`), `note` (optional, 300 characters), unique `[userId, gameMode, dateKey]`
    (sending again replaces the kind and note). Only for an AI mode, only for today or the previous 13 days (the
    archive the hub shows), only from a signed-in member who has a `DailyPuzzleScore` row for that mode and day (they
    finished it). Not a `ContentReport`: a puzzle has no member author and nothing
    to take down for others.
  - **Where:** "Something wrong with this puzzle?" under the result once the member has finished the puzzle (never
    before: it must not hint), opening a small dialog (`components/ui/dialog.tsx`) with the four kinds as a radio
    group and the note.
  - **The admin page** `/admin/daily-puzzles` (`auth: 'admin'`): tabs per mode (`components/ui/tabs.tsx`), and for the
    mode, rows for today, the next two days and the last seven days: source (model or fallback), the puzzle and its
    answer rendered as plain text, the number of reports by kind, and each report's note (with the member's handle, for
    follow-up). "Generate now" creates a future day's row early through `getOrCreateDailyPuzzle`.
  - **Replace:** only for one of the next two days in America/New_York (`todayEST < dateKey <= todayEST + 2`), and
    never within the last 10 minutes before that day starts (a margin for clock skew between the web tier and
    Postgres and for the slow model call). The order is fixed so that a day that has started can never change:
    1. generate the new puzzle **first**, outside any transaction (`generateForMode`, exported from
       `generate.server.ts` for this; the model call takes seconds and must not hold a lock or a row);
    2. then one transaction under `lockKey(tx, 'daily-puzzle:<mode>:<dateKey>')` re-checks, with the time read inside
       it, that the day is still in the window and the margin, that no `DailyPuzzleScore` row exists for the mode and
       day, and that the stored row is the one the admin saw (its `id` and `createdAt`, sent by the page), and only
       then **updates that row in place** (`data`, `source`) — never delete-then-create, which leaves a gap in which
       a visitor's or the prewarm's `getOrCreateDailyPuzzle` writes a different puzzle;
    3. the same transaction records the admin action with `recordAdminActionIn` (`daily-puzzle-replace`, the mode, the
       day, the old and new source; never the puzzle text).
    Any failed check refuses with `PUZZLE_ALREADY_STARTED` (started, in the margin, or scored) or
    `PUZZLE_CHANGED` (the row is not the one the admin saw) and writes nothing. Today's and past puzzles are never
    replaced, because scores already stand against them; for those the page says "Players have already played this
    puzzle". Replacing does not touch the public cache (the public read refuses future days, so nothing is cached for
    them).
  - **Generate now** creates a missing row for one of the next two days through `getOrCreateDailyPuzzle` (which keeps
    its first-writer-wins rule); it never replaces an existing one.
  - **Rate limits:** the report `PUT` is `rateLimit: { limit: 10, windowMs: 3_600_000, prefix: 'puzzle-report',
    scope: 'user' }`; the two admin writes `rateLimit: 'write'`; the admin read `rateLimit: 'read'`.
  - **Export and erasure:** the member's puzzle reports are exported (`puzzleReports`) and erased with the account.

   onDelete: Cascade)`), indexes `[gameMode, dateKey]` and `[userId]`; its back-relation in `model User` under the Wave
   0 anchor; migration `20261228050200_s14_puzzle_reports`.

   dateKey)`, `exportPuzzleReports`, `puzzleReportErasureOps`.
3. FR-3 Contract `lib/daily-puzzles/reports.contract.ts` (new) and modules `lib/daily-puzzles/api/
   daily-puzzles.report.server.ts` (`PUT /api/daily-puzzles/report`), `lib/admin/api/admin.daily-puzzles.server.ts`
   (`GET /api/admin/daily-puzzles?mode=`), `lib/admin/api/admin.daily-puzzles.replace.server.ts`
   (`POST /api/admin/daily-puzzles/replace`) and `lib/admin/api/admin.daily-puzzles.generate.server.ts`
   (`POST /api/admin/daily-puzzles/generate`), all through `implement()`.
4. FR-4 `components/daily-puzzles/ReportPuzzleDialog.tsx` (new), mounted by `PuzzleShell.tsx` after the result for the
   five AI modes.
5. FR-5 `app/routes/_site/admin/daily-puzzles.tsx` (new) and `components/admin/DailyPuzzlesAdmin.tsx` (new); the
   sitemap's `EXCLUDED_ROUTES` line under the Wave 0 anchor; the admin index link where the other admin pages are
   listed (`app/routes/_site/admin/index.tsx`).
6. FR-6 Refusal codes under `// s14-06 puzzle-reports`: `PUZZLE_REPORT_NOT_PLAYED` ("Finish this puzzle before
   reporting it"), `PUZZLE_ALREADY_STARTED` ("Players have already played this puzzle, so it cannot be replaced"),
   `PUZZLE_CHANGED` ("This puzzle changed since you opened it. Reload to see it").
7. FR-7 The erasure registry entry `DailyPuzzleReport: erase`, the operation under the erasure anchor, the export
   property under the export anchor.

## Non-functional requirements

- **No spoilers:** the report entry point appears only after a result; the report endpoint never echoes the answer.
- **Admin only:** every admin module is `auth: 'admin'`; the answer appears only there.
- **Integrity:** a replacement can never change a day that has started or that anyone has a `DailyPuzzleScore` for:
  date, margin and score checks run inside the locked transaction that updates the row in place, with the time read
  inside it; the slow generation happens before the transaction. The report upsert is one `upsert` on the unique
  `[userId, gameMode, dateKey]`, so two concurrent sends leave one row.
- **Query shapes (verify against the schema):** `DailyPuzzle.source` and `data` are required; `DailyPuzzleReport.note`
  is optional; group report counts with `groupBy({ by: ['gameMode', 'dateKey', 'kind'] })`.

## Data model and API

`DailyPuzzleReport` (above). `PUT /api/daily-puzzles/report` `{ gameMode, dateKey, kind, note? }` → `{ ok: true }`.
Admin reads and writes as above.

## Testing requirements

- Main suite `lib/daily-puzzles/__tests__/puzzle-reports.test.ts`: a member without a score row is refused; a second
  report replaces the first; outside the window or a non-AI mode is refused.
- Main suite `lib/daily-puzzles/__tests__/puzzle-replace.test.ts`: a future day is replaced in place and audited;
  today, a past day, a day three days out, a day starting within 10 minutes, a future day with a score row and a row
  that changed since the page read it are refused with nothing written; the lock key is taken before the checks; the
  generator runs before the transaction opens; non-admins are refused.
- Main suite `lib/account/__tests__/puzzle-reports-erasure.test.ts`; the export test (key `puzzleReports`);
  `lib/account/__tests__/erasure-coverage.test.ts`; `lib/__tests__/migration-safety.test.ts`; the sitemap coverage
  test; the error-code catalogue.

## Acceptance criteria

- [ ] After finishing today's Alibi a member reports "Two answers fit" with a note, and the admin page shows it
      against today's Alibi.
- [ ] An admin opens tomorrow's Spectrum, reads its answer, replaces it, and the audit log records it.
- [ ] Replacing today's puzzle is refused with "Players have already played this puzzle".
- [ ] A member's puzzle reports are in their export and gone after erasure.

## Out of scope

Replacing a puzzle already played (and re-scoring), telling reporters about a fix, Lights Out and Globeset (not
model-generated), editing a puzzle by hand.
