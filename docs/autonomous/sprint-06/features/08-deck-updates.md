# 08 — Copied decks get their author's changes

Surface: the deck page (`/study/$deckId`, `app/routes/_site/study/$deckId.tsx`)
of a deck added from the marketplace (`/study/browse`). Wave 1. Namespace
`deck-updates`.

## User story

As a student who added a public deck from the marketplace, I want to know when
its author fixes a card or adds new ones, and to take those changes into my copy
without losing my review progress or my own edits, so that I am not studying a
mistake the author corrected weeks ago.

## Requirements elicitation

- **What exists (verified):**
  - `cloneDeck` (`lib/study.server.ts`) copies a public deck's authored cards
    into a new private deck once, records `FlashcardDeck.clonedFromId`, and is
    idempotent per source. Generated siblings (reversible, cloze; sprint 05 09)
    are regenerated by `insertCards` (`lib/study/deck-editor.server.ts`).
  - The copy keeps no link from a copied card to its source card; review state
    is `FlashcardReview` per user per card (`@@unique([userId, cardId])`).
  - The owner's own edits go through `updateCard`, `addCard`, `deleteCard`,
    `reorderCards` in `deck-editor.server.ts`, which already handle siblings.
- **Decisions:**
  - Each copied authored card records `originCardId` (the source card's id) and
    `originHash` (a hash of the source's `kind`, `front`, `back` at the time it
    was copied or last synced). Cards the member wrote themselves have neither.
  - The deck records `sourceSyncedAt`. "Updates available" compares the
    source's authored cards with the copy:
    - **new** — a source card with no copy card pointing at it;
    - **changed** — a copy card whose `originHash` differs from the source
      card's current hash, *and* whose own content still equals its
      `originHash` (the member has not edited it);
    - **conflict** — changed at the source *and* edited by the member: shown,
      never applied automatically; the member picks "Keep mine" or "Take
      theirs";
    - **removed** — a copy card whose `originCardId` no longer exists in the
      source: offered for removal, never removed automatically.
  - Applying keeps review progress: a changed card is updated in place (same
    row, same `FlashcardReview`); siblings are reconciled by `updateCard`'s
    existing logic (a cloze deletion that disappeared loses only its own review
    row).
  - If the source deck stops being public or is deleted, the copy says "The
    original is no longer shared" and offers nothing; the copy is untouched.
  - Members choose per deck "Tell me about updates" (default on); when on, a
    weekly check (the existing deck page load is enough — no job) shows the
    banner; no notifications are sent (keeps it quiet and job-free).
  - The 2 000-row cap per deck (`lib/study/limits.ts`) applies: an update that
    would exceed it applies as many new cards as fit and says how many were
    left out.

## Functional requirements

1. FR-1 On a copied deck whose source has updates, the deck page shows one line
   on a rule: "The author changed 3 cards and added 12. Review updates", only to
   the deck owner.
2. FR-2 "Review updates" opens a dialog with segments (`components/ui/tabs.tsx`)
   New, Changed, Conflicts, Removed; each row shows the card (and for changed
   rows a word diff using the existing `lib/feed/word-diff.ts`) with a checkbox;
   "Apply selected" is the ink primary.
3. FR-3 Conflicts show both versions with "Keep mine" / "Take theirs" per card.
4. FR-4 After applying, `sourceSyncedAt` and the applied cards' `originHash`
   are updated; skipped cards stay pending; "Keep mine" sets `originHash` to the
   source's current hash so the conflict is not shown again until the next
   source change.
5. FR-5 Decks copied before this feature (no `originCardId`) get a one-time
   "Link to the original" action that matches cards by exact `front` text, then
   behaves as above; unmatched cards are left as the member's own.
6. FR-6 A per-deck switch "Tell me about updates" in the deck's settings.

## Non-functional requirements

- **Correctness:** apply runs in one transaction after
  `lockKey(tx, 'deck-sync:' + deckId)`, re-reading the source inside the
  transaction; a card is updated only if its current content still matches what
  the dialog showed (an `expectedHash` per row; mismatches are skipped and
  reported).
- **Security:** `auth: 'required'`; `rateLimit: 'write'` for apply; only the
  copy's owner may read the diff or apply; the source must still be public;
  zod for card ids (≤ 2 000).
- **Performance:** the diff is computed from two `select`s (source authored
  cards, copy authored cards with origin columns), hashing in memory; the
  banner's check runs in the deck loader only for copied decks and is skipped
  when the source's `cardsChangedAt` is set and older than `sourceSyncedAt` (null, a deck untouched since this release, is diffed).
  `FlashcardDeck.updatedAt` cannot serve: `updateCard`
  (`lib/study/deck-editor.server.ts`) writes only `flashcard` rows, so a typo
  fix never moves the deck's `updatedAt` (and `addCard` / `deleteCard` touch it
  only through `cardCount`). Every authored-card mutation in
  `deck-editor.server.ts` (`updateCard`, `addCard`, `deleteCard`, `insertCards`
  when the deck already had cards) sets `cardsChangedAt = now()` on the deck in
  the same transaction; `reorderCards` does not.
- **Privacy:** no new personal data beyond a per-deck preference; nothing to
  erase beyond the deck itself (already handled); export includes the
  preference with the deck.
- **i18n:** `deck-updates`.
- **Steel:** one line on a rule, not a banner box (D8 is open); dialog overlay;
  rows on rules; one ink primary.
- **Accessibility:** the diff marks insertions and deletions with text
  (`<ins>`/`<del>` and visually hidden "added"/"removed"), not colour alone.

## Data model and API

- `Flashcard` gains `originCardId String? @db.VarChar(30)` and `originHash
  String? @db.VarChar(64)`; `FlashcardDeck` gains `sourceSyncedAt DateTime?`,
  `cardsChangedAt DateTime?` and `notifyUpdates Boolean @default(true)` in
  `prisma/schema/rmhstudy.prisma`.
  No new index: lookups go through the existing `@@index([deckId])`. Migration
  `20261126010100_s06_deck_updates`.
- `cloneDeck` sets `originCardId` and `originHash` on the copies;
  `insertCards` accepts them as optional inputs (generated siblings never carry
  them).
- `lib/study/deck-sync.ts` (pure: `cardHash`, `diffDecks`, conflict rules,
  front-text matching), `deck-sync.server.ts` (`deckUpdates`, `applyUpdates`,
  `linkToOriginal`), `deck-sync-schema.ts`, `deck-sync.contract.ts`.
- Modules `lib/study/api/study.decks.$id.updates.server.ts` (GET diff, POST
  apply), `study.decks.$id.link-original.server.ts` (POST).
- `components/study/DeckUpdatesLine.tsx`, `DeckUpdatesDialog.tsx`; the switch
  in the deck settings form.

## Testing requirements

- Main suite `lib/study/__tests__/deck-updates.test.ts`: only the owner reads or
  applies; a private source returns nothing; apply keeps the card id and its
  review row; an edited card becomes a conflict, not an overwrite; editing one
  card on the source sets its `cardsChangedAt` and the copy's banner appears; a
  stale
  `expectedHash` is skipped; the row cap is honoured; the lock is taken first.
- Product suite `lib/study/__tests__/deck-sync.product.test.ts`: `diffDecks`
  for new, changed, conflict, removed; hash stability; front-text matching with
  duplicates (first unmatched wins).
- The existing clone and editor tests stay green.

## Acceptance criteria

- [ ] An author fixes a typo on a public deck; the student who copied it sees
      "The author changed 1 card", applies it, and the card keeps its due date.
- [ ] A card the student edited shows as a conflict and is not overwritten.
- [ ] New cards appear in the copy as new (never reviewed) cards.
- [ ] A deck copied before this release can be linked and then updated.
- [ ] Day and Night, 390 px and 1280 px, `ar`.

## Out of scope

Pushing the student's edits back to the author, notifications, syncing decks
between two members' private decks.
