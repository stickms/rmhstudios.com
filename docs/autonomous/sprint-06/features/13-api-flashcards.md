# 13 — Flashcards in the developer API

Surface: the public developer API (`/api/v1/me/decks*`), its OpenAPI document
and the developer docs; the key-creation UI lists the new scopes from
`lib/api/scopes.ts`. Wave 6 (after 08 and 12). No namespace (scope and docs text
is English data in `lib/`, as for every existing scope).

## User story

As a student who writes notes in my own tool, I want a script to create and
update my RMH Studios flashcard decks and read what is due, so that my cards
stay in step with my notes without exporting and importing files by hand.

## Requirements elicitation

- **What exists (verified):**
  - Decks and cards: `FlashcardDeck`, `Flashcard` (`kind` basic, reversible,
    cloze; generated siblings carry `sourceId`, sprint 05 09),
    `FlashcardReview` (`prisma/schema/rmhstudy.prisma`). Server logic in
    `lib/study.server.ts` (`listDecks`, `getDeck`) and
    `lib/study/deck-editor.server.ts` (`updateDeck`, `insertCards`, `addCard`,
    `updateCard`, `deleteCard`, `importCards`), with limits in
    `lib/study/limits.ts`.
  - The developer API has no study endpoints (`app/routes/api/v1/**`), and no
    `read:study` / `write:study` scope (`lib/api/scopes.ts`).
  - v1 routes are route files wrapped in `withDeveloperApi` (key auth, scopes,
    key restrictions from sprint 03 06, idempotency keys
    `ApiIdempotencyKey`, usage counting).
- **Decisions:**
  - Scopes `read:study` (decks, cards, due counts) and `write:study` (create,
    update, delete decks and authored cards). Reviews are **not** writable
    through the API: grading belongs in the review UI, and a script grading
    cards would corrupt the member's own statistics.
  - Only authored cards are exposed and written; generated siblings are
    regenerated by the existing editor functions exactly as in the UI.
  - Every write goes through the same server functions the UI uses, so every
    limit (deck count, 2 000-row cap, field lengths) and every side effect
    (`cardCount`, sibling generation, 08's origin columns left untouched)
    applies unchanged.
  - Cards carry an optional `externalId` (≤ 100 characters, unique per deck)
    so a script can upsert idempotently: `PUT /api/v1/me/decks/{id}/cards/by-external-id/{externalId}`.
  - Public decks of other members are not exposed (the marketplace is a
    browsing UI); only the key owner's decks.
  - `POST` writes honour the existing `Idempotency-Key` header support of
    `withDeveloperApi`.

## Functional requirements

1. FR-1 `GET /api/v1/me/decks` — the owner's decks (id, title, description,
   isPublic, cardCount, dueCount, updatedAt), cursor paginated.
2. FR-2 `POST /api/v1/me/decks` — create (title, description, isPublic).
3. FR-3 `GET|PATCH|DELETE /api/v1/me/decks/{id}`.
4. FR-4 `GET /api/v1/me/decks/{id}/cards` — authored cards (id, kind, front,
   back, position, externalId), cursor paginated; `POST` adds up to 100 cards
   in one request (one transaction, all or nothing).
5. FR-5 `PATCH|DELETE /api/v1/me/decks/{id}/cards/{cardId}`.
6. FR-6 `PUT /api/v1/me/decks/{id}/cards/by-external-id/{externalId}` — create
   or update by external id.
7. FR-7 `GET /api/v1/me/decks/{id}/due` — counts due now and in the next 24
   hours (no card content), for "you have 40 cards due" widgets.
8. FR-8 Each endpoint is in `lib/api/registry.ts` with examples; the scopes have
   descriptions and the "Study" group in `lib/api/scopes.ts`.

## Non-functional requirements

- **Security:** `withDeveloperApi` with the scopes above; zod for every body,
  path and query value (ids ≤ 64, `limit` ≤ 100, card fields with the UI's
  limits); a deck id that is not the key owner's returns 404, never 403 (no
  existence oracle). Writes also count toward the key's rate limit and the
  `rateLimit: 'write'` budget of the member.
- **Correctness:** batch create is atomic; external id uniqueness is enforced
  by a unique index and the upsert runs in a transaction after
  `lockKey(tx, 'deck-cards:' + deckId)`.
- **Performance:** list endpoints use keyset pagination on (`position`, `id`)
  for cards and (`updatedAt`, `id`) for decks; due counts use the existing
  `@@index([userId, dueAt])`.
- **Privacy:** no other member's data; `externalId` is the member's own data and
  is included in the account export with the deck (the export already lists
  decks; add the field if fields are listed explicitly).
- **Developer API:** additive only; webhooks are not added for study (out of
  scope).

## Data model and API

- `Flashcard.externalId String? @db.VarChar(100)` with `@@unique([deckId,
  externalId])` (Postgres treats nulls as distinct, so existing rows are
  unaffected). The `flashcard` table is large: the unique index is created
  `CONCURRENTLY` in its own migration. Migrations
  `20261126060100_s06_flashcard_external_id` (column),
  `20261126060101_s06_flashcard_external_id_index` (CONCURRENTLY, one
  statement), `20261126060102_s06_flashcard_external_id_index_ensure_valid`.
- `lib/api/v1/study.server.ts` (thin adapters from v1 shapes to the existing
  study functions), `lib/api/v1/study-schema.ts`. Deck create and delete have no
  server function today: they are inline in the UI modules
  (`lib/study/api/study.decks.server.ts` creates with its limits,
  `lib/study/api/study.decks.$id.server.ts` deletes). Extract each into
  `createDeck` / `deleteDeck` in `lib/study/deck-editor.server.ts`, call them
  from both the UI module and the v1 route, and keep the UI behaviour
  unchanged (a move, not a rewrite; 08 has already merged into these files).
- Route files `app/routes/api/v1/me/decks.ts`, `me/decks/$id.ts`,
  `me/decks/$id/cards.ts`, `me/decks/$id/cards/$cardId.ts`,
  `me/decks/$id/cards/by-external-id/$externalId.ts`, `me/decks/$id/due.ts`.
- `lib/api/scopes.ts` (two scopes), `lib/api/registry.ts` (entries).

## Testing requirements

- Main suite `lib/api/__tests__/v1-study.test.ts`: scopes enforced per method;
  another member's deck is 404 on every endpoint; generated siblings never
  listed and never writable; batch of 101 refused; a batch with one invalid
  card writes nothing; 2 000-row cap enforced; upsert by external id is
  idempotent under the lock; reviews cannot be written (no route).
- Product suite `lib/api/__tests__/v1-study-schema.product.test.ts`: schema
  limits and cursor encoding.
- The scope catalog test and the OpenAPI snapshot stay green after
  `pnpm docs:api` (integration).

## Acceptance criteria

- [ ] With a `write:study` key, a script creates a deck and 100 cards in one
      call; they appear in `/study` with siblings for reversible cards.
- [ ] Running the same upsert twice changes nothing the second time.
- [ ] A `read:study` key cannot write; a key without study scopes cannot read.
- [ ] `GET …/due` matches the due count on the deck page.

## Out of scope

Writing reviews, reading other members' public decks, study webhooks.
