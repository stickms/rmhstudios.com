# 01 · Contrast checker (`/tools/contrast`)

Category:
Developer.
Branch:
`autonomous/s01-contrast`.
Status:
shipped
in
sprint 01.

## User story

As
a
member
who
designs
a
profile
theme,
a
vibe
or
a
page,
I
want
to
check
a
text
and
background
colour
pair
against
WCAG
2.2
so
that
what
I
make
is
readable
by
everyone,
and
to
get
the
nearest
colour
that
passes
when
it
is
not.

## Requirements elicitation

Who:
members
of
the
site
(and
signed-out
visitors,
since
every
tool
is
public)
who
would
otherwise
paste
the
same
data
into
an
unknown
third-party
website.
Why
here:
the
site
already
hosts
the
developer
API,
RMHCode,
RMHStudy,
the
vibes
platform,
communities
and
group
chats;
these
are
the
jobs
those
users
do
next
to
them.
Constraints
from
the
repository:
Steel
design
language,
`t()`
for
every
string,
a
public
route
with
its
own
meta
and
an
OG
card,
no
server
round
trip
for
user
data,
and
no
new
dependency.

## Specification

### Functional requirements

- **F1.**
  Accept
  colours
  as
  #rgb,
  #rgba,
  #rrggbb,
  #rrggbbaa
  (with
  or
  without
  #),
  rgb()/rgba()
  and
  hsl()/hsla()
  in
  comma
  or
  space
  syntax;
  alpha
  is
  ignored.
- **F2.**
  Each
  colour
  has
  a
  native
  colour
  picker
  and
  a
  text
  field
  kept
  in
  sync;
  an
  unreadable
  value
  shows
  an
  inline
  error.
- **F3.**
  Show
  the
  WCAG
  contrast
  ratio,
  rounded
  down
  to
  two
  decimals
  so
  a
  displayed
  pass
  is
  a
  real
  pass.
- **F4.**
  Show
  pass
  or
  fail
  for
  AA
  body
  text
  (4.5:1),
  AA
  large
  text
  (3:1),
  AAA
  body
  (7:1),
  AAA
  large
  (4.5:1)
  and
  non-text
  UI
  (3:1),
  by
  icon
  and
  word,
  not
  colour
  alone.
- **F5.**
  Preview
  both
  text
  sizes
  in
  the
  chosen
  pair.
- **F6.**
  When
  AA
  body
  text
  fails,
  suggest
  the
  colour
  of
  the
  same
  hue
  and
  saturation
  at
  the
  nearest
  lightness
  that
  reaches
  4.5:1,
  with
  copy
  and
  apply
  actions.
- **F7.**
  Swap
  the
  two
  colours.
- **F8.**
  Keep
  a
  valid
  pair
  in
  the
  URL
  (?fg=&bg=,
  six
  hex
  digits)
  so
  a
  result
  can
  be
  shared;
  invalid
  query
  values
  fall
  back
  to
  the
  defaults.

### Non-functional requirements

- **Privacy
  and
  security.**
  Everything
  runs
  in
  the
  browser;
  no
  input
  is
  sent
  to
  the
  server,
  logged
  or
  stored,
  except
  where
  a
  requirement
  above
  names
  local
  storage.
  Randomness,
  where
  used,
  is
  `crypto.getRandomValues`
  through
  `lib/toolbox/random.ts`
  (rejection-sampled),
  never
  `Math.random()`.
- **Performance.**
  Pure
  functions
  with
  no
  dependency;
  work
  proportional
  to
  the
  input,
  bounded
  by
  explicit
  limits;
  expensive
  recomputation
  deferred
  with
  `useDeferredValue`
  where
  input
  is
  long.
  Nothing
  animates
  or
  polls
  at
  rest
  (Steel
  R5);
  no
  worker,
  observer
  or
  animation
  frame.
- **Accessibility.**
  Every
  control
  is
  labelled
  (`Label`/`aria-label`),
  results
  that
  change
  are
  in
  an
  `aria-live`
  region,
  errors
  use
  `role="alert"`,
  state
  is
  never
  conveyed
  by
  colour
  alone,
  focus
  ring
  is
  the
  global
  K10
  outline,
  and
  tab
  switchers
  use
  the
  shared
  `Tabs`
  (roving
  keyboard).
- **Design
  system
  (Steel).**
  `ToolFrame`
  (PageLayout),
  rows
  on
  1px
  rules
  (R3),
  `--site-*`
  token
  utilities
  only,
  `t-*`
  type
  classes,
  at
  most
  one
  ink
  primary
  button
  per
  view
  (R4),
  no
  gradient,
  blur,
  shadow
  or
  translucency
  (R1).
- **i18n.**
  All
  strings
  through
  `t()`
  in
  the
  `toolbox`
  namespace
  with
  literal
  defaults;
  numbers
  and
  dates
  through
  `Intl`
  in
  the
  active
  locale;
  layouts
  survive
  RTL
  (`ar`).
- **SSR.**
  Output
  that
  depends
  on
  the
  clock,
  the
  viewer's
  time
  zone
  or
  randomness
  renders
  only
  after
  hydration,
  so
  server
  and
  client
  agree.
- **SEO.**
  `definePage`
  gives
  the
  route
  its
  own
  title,
  description
  and
  canonical;
  it
  unfurls
  with
  the
  `/tools`
  section
  card;
  it
  is
  listed
  in
  the
  sitemap
  from
  the
  catalog.

- Logic:
  `lib/toolbox/contrast.ts`
  (pure,
  strict-island
  typed).
- UI:
  `components/toolbox/contrast/ContrastTool.tsx`
  inside
  `ToolFrame`.
- Route:
  `app/routes/_site/tools/contrast.tsx`;
  catalog
  entry
  in
  `lib/toolbox/catalog.ts`.

  `lib/toolbox/__tests__/contrast.test.ts`
  in
  the
  Toolbox
  suite
  (`pnpm test:toolbox`).
