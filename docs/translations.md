# Translations

The
site
and
the
docs
ship
in
the
same
9
languages:
`en`
plus
`zh`,
`ar`,
`hi`,
`es`,
`fr`,
`pt`,
`ru`
and
`ja`.
That
list
mirrors
`LOCALES`
in
`lib/i18n/config.ts`;
the
app
and
the
docs
deliberately
support
the
same
set,
so
a
reader
who
uses
the
site
in
Japanese
isn't
dropped
into
English
documentation.
`ar`
is
right-to-left,
matching
`RTL_LOCALES`
in
the
same
module.

English
is
authoritative.
Everything
is
written
in
English
first
and
translated
from
it.

`de`,
`ko`,
`it`,
`id`,
`tr`,
`ur`
and
`vi`
shipped
until
2026-11-17
and
were
parked
to
cut
translation
spend.
They
sit
in
`PENDING_LOCALES`
with
the
other
unshipped
catalogs:
their
files
under
`locales/`
and
`docs/locale/`
are
kept,
nothing
serves
them,
and
nothing
translates
them.
Promoting
one
again
pays
only
for
the
keys
added
since
it
was
parked.

## Site strings (`locales/`)

The
UI
catalogs
are
translated
by
the
**i18n-translate**
GitHub
Actions
workflow
(`.github/workflows/i18n-translate.yml`),
never
on
a
laptop.
Run
it
from
the
Actions
tab
(**Run
workflow**).
It
has
two
inputs:
`locales`
(a
comma-separated
subset;
empty
means
every
shipped
locale)
and
`dry_run`
(report
what
would
be
paid
for
and
stop).
It
uses
the
`DEEPSEEK_API_KEY`
repository
secret.

A
run
translates
only
what
is
missing
or
stale,
and
pays
for
each
string
at
most
once:

- **Already
  current
  is
  skipped.**
  `locales/<lng>/.sources.<ns>.json`
  records
  the
  English
  each
  translation
  was
  made
  from.
  A
  key
  whose
  recorded
  English
  matches
  today's
  English
  is
  never
  sent
  again,
  and
  a
  human
  edit
  to
  a
  translation
  survives
  until
  its
  English
  changes.
- **Unmerged
  work
  is
  reused.**
  Each
  run
  pushes
  its
  output
  to
  the
  `i18n/auto-translate`
  branch
  and
  opens
  (or
  updates)
  one
  pull
  request
  from
  it.
  Before
  any
  model
  call,
  `scripts/i18n-collect-reuse.ts`
  gathers
  every
  translation
  stored
  on
  any
  `i18n/*`
  branch
  (that
  pull
  request,
  and
  the
  per-run
  branches
  the
  previous
  workflow
  left
  unmerged),
  and
  the
  translator
  adopts
  each
  one
  whose
  recorded
  English
  is
  still
  today's
  English.
  A
  run
  that
  happens
  before
  the
  pull
  request
  merges
  does
  not
  pay
  again.
- **Identical
  English
  is
  translated
  once.**
  Within
  a
  locale,
  a
  string
  that
  already
  has
  a
  current
  translation
  under
  any
  key
  (`Cancel`,
  `Save`,
  `{{count}} players`)
  is
  copied
  rather
  than
  sent,
  and
  a
  string
  that
  appears
  under
  several
  untranslated
  keys
  is
  sent
  once.
- **Strings
  without
  words
  are
  copied.**
  Numbers,
  symbols
  and
  bare
  placeholders
  (`10`,
  `—`,
  `{{done}}/{{total}}`)
  read
  the
  same
  everywhere
  and
  are
  never
  sent.
- **Plural
  forms
  follow
  the
  language.**
  English
  has
  `_one`
  and
  `_other`;
  Japanese
  and
  Chinese
  use
  only
  `_other`,
  Russian
  adds
  `_few`
  and
  `_many`,
  Arabic
  uses
  all
  six
  CLDR
  forms.
  The
  translator
  asks
  for
  exactly
  the
  forms
  each
  language
  uses
  (`Intl.PluralRules`),
  never
  writes
  the
  others,
  and
  never
  commits
  a
  plural
  group
  or
  a
  new
  namespace
  file
  half-filled
  by
  reuse
  alone,
  so
  its
  pull
  request
  passes
  `lib/__tests__/i18n-catalogs.test.ts`.

GitHub
Actions
may
not
be
allowed
to
open
pull
requests
in
this
repository
(Settings
→
Actions
→
General
→
"Allow
GitHub
Actions
to
create
and
approve
pull
requests").
The
run
then
stays
green,
pushes
the
branch
anyway,
and
prints
a
compare
link
in
the
job
summary;
open
the
pull
request
from
that
link.
The
paid
work
is
safe
on
the
branch
either
way.

`I18N_LOCALES`,
`I18N_DRY_RUN`
and
the
other
knobs
at
the
top
of
`scripts/translate-locales.ts`
are
what
the
workflow
sets;
the
script
can
still
be
run
by
hand
with
a
DeepSeek
key,
but
the
workflow
is
the
supported
path
because
it
is
the
one
that
reuses
the
pending
branch.

## Docs pages (`docs/locale/`)

### How it works

Sphinx
uses
gettext.
Catalogs
live
in
`docs/locale/<lang>/LC_MESSAGES/`,
one
`.po`
file
per
document
(`gettext_compact = False`),
and
fall
back
**per
string**:
an
untranslated
paragraph
renders
in
English
while
the
rest
of
the
page
stays
translated.
A
partially
translated
page
is
therefore
usable
rather
than
broken,
which
is
what
makes
incremental
translation
viable
at
all.

### Coverage

Translations
are
maintained
for
the
reader-facing
pages:

| Page                     | Why                                                                                                  |
| ------------------------ | ---------------------------------------------------------------------------------------------------- |
| `index`                  | The docs landing page.                                                                               |
| `site-reference/index`   | What the platform is.                                                                                |
| `developer-api/*` guides | Overview, authentication, scopes, rate limits, errors, pagination, idempotency, webhooks, changelog. |

Deliberately
**not**
translated:

- **`developer-api/endpoints/*`**
  —
  the
  generated
  endpoint
  reference.
  It
  is
  mostly
  HTTP
  verbs,
  paths,
  JSON
  bodies
  and
  one-line
  summaries;
  the
  translatable
  fraction
  is
  small,
  and
  it
  regenerates
  whenever
  the
  registry
  changes,
  which
  would
  invalidate
  the
  translations
  on
  every
  API
  change.
- **`developer-api/internals.md`**
  and
  the
  rest
  of
  `docs/`
  —
  ~190
  dated
  design
  docs,
  plans,
  audits
  and
  per-game
  specs.
  These
  are
  internal
  working
  documents
  written
  for
  contributors,
  they
  churn
  constantly,
  and
  machine-translating
  them
  would
  add
  tens
  of
  thousands
  of
  catalog
  entries
  that
  nobody
  reads.

The
subset
lives
in
`TRANSLATED`
in
`scripts/docs-i18n.sh`.
To
start
translating
another
page,
add
its
docname
there
and
run
`extract`
then
`update`.

### Workflow

```bash
pip install -r docs/requirements.txt sphinx-intl

scripts/docs-i18n.sh extract          # English sources → .pot
scripts/docs-i18n.sh update           # merge into every locale's .po
scripts/docs-i18n.sh build ja         # build one language locally
scripts/docs-i18n.sh stats            # per-locale translated/untranslated counts
```

`update`
**merges**:
a
string
whose
English
text
changed
is
marked
`fuzzy`
with
its
old
translation
kept,
rather
than
silently
discarded.
Fuzzy
entries
are
ignored
at
build
time
—
the
page
falls
back
to
English
for
that
string
until
someone
re-translates
it.
So
editing
English
prose
degrades
a
translation
gracefully
instead
of
leaving
a
stale
claim
in
place,
which
is
the
failure
mode
that
matters.

### Rules for translators

- Never
  touch
  `msgid`.
  Only
  fill
  in
  `msgstr`.
- Leave
  the
  contents
  of
  inline
  code
  spans
  in
  English
  —
  identifiers,
  file
  paths,
  HTTP
  header
  names,
  scope
  ids,
  error
  codes
  and
  route
  paths
  are
  part
  of
  the
  API,
  not
  prose.
  `` `read:profile` ``
  is
  a
  literal
  value
  a
  developer
  types.
- Preserve
  Markdown
  and
  MyST
  syntax
  exactly,
  including
  directive
  names
  (```{note}),
  roles,
  and
  link
  targets.
  Translate
  link
  _text_,
  never
  the
  target.
- Don't
  translate
  brand
  names
  or
  URLs.
- For
  `ar`
  (and
  any
  RTL
  locale
  promoted
  later),
  do
  not
  insert
  Unicode
  directional
  control
  marks.
  Pages
  render
  with
  `dir="rtl"`
  and
  the
  browser's
  bidi
  algorithm
  handles
  mixed-script
  runs;
  embedded
  control
  characters
  corrupt
  output
  and
  are
  invisible
  in
  review.

### Read the Docs setup

Read
the
Docs
models
translations
as
**separate
projects
linked
to
a
parent**,
not
as
one
multilingual
build.
For
each
language:

1. Create
   a
   project
   pointing
   at
   the
   same
   repository,
   named
   e.g.
   `rmhstudios-ja`.
2. Set
   its
   **Language**
   to
   that
   locale
   in
   the
   project's
   settings.
3. On
   the
   English
   project,
   add
   it
   under
   **Translations**.

RTD
then
passes
`-D language=<code>`
to
Sphinx
and
serves
the
result
at
`/<code>/`,
with
the
language
switcher
in
the
flyout
wired
up
automatically.
`docs/conf.py`
sets
`language = "en"`
and
is
otherwise
identical
across
every
project
—
nothing
per-language
is
committed
except
the
catalogs.

When
a
language
is
parked
(taken
out
of
`LOCALES`),
remove
its
project
from
the
English
project's
**Translations**
list
so
the
flyout
stops
offering
it.
The
project
itself
can
be
deactivated
rather
than
deleted;
its
catalogs
stay
in
the
repository.
