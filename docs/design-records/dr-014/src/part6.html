Chapter Twenty-two

Hit testing sixteen wedges

There is no hit-testing code. Sixteen full-size overlapping squares, each clipped to a pie sector, and a browser that already knows a clip bounds pointer events. The only real work is switching the wrappers off so they do not blanket the disc.

22.1 The mechanism

Each wedge is a list item filling the whole dial square, containing an anchor that also fills the whole square, clipped to its sector. Sixteen of those, stacked. Without intervention the topmost one in DOM order catches every click on the entire disc.

{{code:components/radial/radial.css|1077-1086|Why the wrappers are click-transparent}}

The wrappers are pointer-events: none; the clipped anchors set pointer-events: auto. So a pointer event tests only against the clipped regions, and because the clip is the exact sector polygon, each anchor catches only what is inside its own sector. The sectors tile the annulus with 1.4° gaps — which means a press exactly in a divider hits nothing, by design, rather than being resolved arbitrarily.

The glyph wrapper inside each anchor is also pointer-events: none, so clicks fall through it to the sector beneath. That matters because the glyph box is an axis-aligned rectangle centred on the sector's centroid, and near the dividers its corners extend into neighbouring territory. Left hit-testable, a label's corner would steal a neighbour's click in exactly the region where the user is aiming at a visible boundary.

22.2 Target sizes, honestly

The platform's touch-target floor is 44 pixels, published as --site-touch-target. A wedge is not square, so the question is what "44 pixels" means for an annulus sector.

The honest reading: at 320 pixels the wedges are a few pixels short of the floor in the radial direction, and comfortably over it in the angular direction. A 41×55 target is larger in area than a 44×44 one, and the shortfall is in the axis where the neighbour is a different ring separated by a drawn 9-pixel gap rather than an adjacent target. A miss lands in the gap, not on the wrong destination.

That is a defensible position and it is not the same as meeting the guideline. It is recorded in Chapter 30 among the open items, because the cleanest fix — lifting the dial's 86vw to something larger below 360px — has a knock-on effect on the foot pill's clearance that nobody has worked through.

22.3 The pointer metaball, and AUD-503

The hub shares the module — and the filter bank — with the site's pointer metaball: a gooey drop that follows the mouse on desktop and the finger on touch, replacing the native cursor while it is driving one.

Its contract is worth reading as a piece of engineering discipline in its own right. Every spring converges at a fixed rate per second — 1 − e^(−λ·dt) — rather than a fixed fraction per frame, so a 144Hz display gets the same curve as a 60Hz one instead of snapping to the pointer, and a dropped frame produces no jump. dt is clamped so returning to a backgrounded tab eases rather than teleports. The filter region is a fixed box with every blob offset clamped inside it, so the tail can stretch but can never enlarge or escape the region being blurred. will-change is toggled by the loop, so a parked pointer holds no compositor layer.

And it had the most quotable defect in the audit. AUD-503: the drop swelled ×1.85 over interactive elements — largest precisely when covering a control's label. "Play now" read as "▷ ●now". An effect designed to say this is interactive was obscuring the words that said what it was.

The repair caps the swollen diameter at about 22 pixels and thins the fill as it swells, so text reads through. Which is the same lesson as Chapter 18's two-layer split, arriving from a different direction: a decorative liquid effect must never occupy the same pixels as something you have to read. The dial solved it with a layer split; the cursor solved it with an opacity ramp; both are the same rule.

Legibility built into the shape

Because the drop uses no blend mode, there is no inversion to rely on for contrast. So it is filled with --site-text and carries a halo in --site-bg — two drop-shadows chained after the goo, so the rim traces the fused outline rather than each blob. Those tokens are contrast-paired by definition, so it reads in every theme. On the default theme, where the accent is the ink, hovering the compose button turns the whole mark into its own halo and it reads as a ring — a coincidence the code anticipates in a comment.

22.4 What the hub does not do with the pointer

No press-and-drag selection. No radial gesture recognition. No angular velocity. The dial is sixteen links and a pointer, and hovering one fills it and names it, and pressing it navigates.

This is a non-goal from Chapter 4, and the reason bears repeating here where the input model is under discussion: gesture-driven radial menus work in games because the player has hours of muscle memory and a fixed item set. A website's navigation is used by someone who arrived thirty seconds ago from a search engine. Any interaction that must be learned before it can be used is, for that person, a wall.

Chapter Twenty-three

Keyboard and screen reader

A radial menu is a visual metaphor. To a screen reader it is a list of sixteen links with a name, and to a keyboard it is sixteen tab stops. Both of those are fine, and the parts that are not fine are worth naming precisely.

23.1 The semantics, as shipped

The accessibility surface

The last row is the one most often got wrong in overlay components, and getting it right matters more than it sounds. A hidden menu whose links remain focusable produces a tab order with sixteen invisible stops in it — a keyboard user tabs from the page's last control into nothing, sixteen times. The hub computes const tab = menuVisible ? 0 : -1 once and applies it to every interactive element in the overlay.

23.2 What is missing

Three gaps, stated plainly rather than buried.

No arrow-key navigation. The ARIA authoring practices for a menu expect arrow keys to move between menuitems, with Tab moving out of the menu entirely. The hub gives every wedge a real tab stop and no arrow handling, so it behaves like a list of links that happens to be labelled as a menu. For a radial layout the mapping is not obvious — should Right go clockwise, or to the next item, and what do Up and Down mean on a ring? — but "not obvious" is not the same as "not required".

No focus trap. Tab past the last wedge and focus continues to the foot pill, and past that into the document behind the overlay — which is aria-hidden and covered, so focus lands somewhere invisible.

No focus restore. Closing the dial does not return focus to the orb. A keyboard user who opens the menu and presses Escape is left with focus wherever it was inside a now-unmounted overlay.

All three are in Chapter 30. None of them prevents the menu from being used with a keyboard; each of them makes it worse than it should be.

23.3 Focus visibility, and the one place it is suppressed

A wedge's :focus-visible deliberately removes the outline:

.radial-hub__wedge:focus-visible { outline: none; }

This is normally a red flag. It is defensible here because the same selector list — :hover, :focus-visible, .is-active — fills the sector with the accent colour and flips its glyph to the accent's contrast ink. The focused wedge is not subtly outlined; it is the one wedge on the dial that is a solid block of accent. An outline on top of that would have to trace the sector's clip path, which it cannot — an outline follows the border box, and the border box here is the whole dial square, so the "focus ring" would be a rectangle around the entire menu.

The orb, whose border box is its own disc, keeps a real ring: outline: 3px solid var(--site-text); outline-offset: 3px.

The test for suppressing a focus ring

Removing outline is acceptable only when the same state produces an indication that is at least as strong and does not depend on colour perception alone. A full-sector fill with an inverted glyph passes: it changes the shape's value, not just its hue. A border brighten on a transparent fill does not — which the audit also caught, as AUD-118, on the outline button variant.

23.4 Translation

Every string in the hub goes through t() with an English defaultValue: the orb's label, the dial's label, the scrim's and close button's "Close", "Settings", "Sign out", "Sign in", and each of the sixteen destination names via its catalog tKey. Sixteen locales, two of them right-to-left.

The audit surfaced a subtle hazard in this arrangement. The orb's shipped English catalog entry is "Open menu"; the code's defaultValue is "Open navigation". Both are fine strings; they are different strings, and the live accessible name is whichever the catalog supplies. The audit's own harness selected the orb by accessible name and silently captured nothing.

The general form: a defaultValue is a fallback, not documentation. Anything that depends on the accessible name — a test, a screenshot harness, an analytics selector — must read the catalog, not the component. And a drift between the two is invisible in the UI, which is what makes it durable.

Chapter Twenty-four

The caption in the hole

Below 480 pixels the dial is sixteen unlabelled glyphs, which the audit correctly called recall rather than recognition. There is no room for sixteen labels on a 320-pixel dial. There is room for one, in the middle.

24.1 The finding

AUD-504(a), rated as part of a P1 group: the mobile dial is entirely icon-only — sixteen unlabelled glyphs as the sole navigation. Desktop wedges showed labels; phones did not. Chapter 12 established that this was not an oversight but arithmetic: the outer band on a 275-pixel dial gives each destination a box of roughly 37×38 pixels, and no typography puts "Adaptive Intelligence" in it.

So the fix could not be "add the labels back". It had to find room that was not there.

24.2 The hole is the room

The dial's centre hole exists to clear the orb — radius 19, which on a 275-pixel dial is a 104-pixel-wide circle. The orb itself is 56 pixels. That leaves an annulus of empty space inside the hole, and empty space in the middle of a dial is the one region every sector is equidistant from.

{{code:components/radial/radial.css|1252-1273|The centre caption}}

The component tracks which destination the pointer or focus is on, in a single piece of state:

{{code:components/radial/RadialHub.tsx|113-121|The hovered-label state, and why}}

Four handlers per wedge set and clear it — onPointerEnter, onPointerLeave, onFocus, onBlur — so it responds to both the pointer and the keyboard. The clear handlers are guarded: setHoveredLabel((cur) => (cur === label ? null : cur)), so a leave event arriving after the next wedge's enter event cannot blank a label that has already been replaced. That ordering does happen, on touch especially, and without the guard the caption flickers.

An effect keyed on the phase clears the caption when the menu closes, so reopening never briefly shows the last thing you touched.

24.3 Exact complementarity

The caption and the per-wedge labels are exact complements, and both halves are declared in the same media query:

.radial-hub__wedge-label { display: none; }        /* base: phones */
.radial-hub__caption    { /* visible */ }

@media (min-width: 480px) {
  .radial-hub__wedge-label { display: -webkit-box; }
  .radial-hub__caption     { display: none; }
}

Exactly one of them is showing a name at any width. That is not merely tidy — it is the thing that makes the mechanism honest. A caption that also appeared on desktop would duplicate the label under the pointer, and the reader would have two sources for the same fact. A caption that appeared on neither would be the original bug.

The caption's own geometry has one deliberate oddity: padding-top: 2.6rem. It is centred on the dial's midpoint, and the orb is also there — so the padding pushes the text below the orb rather than behind it. It is a single-property solution to what would otherwise be an offset calculation against the orb's size token.

24.4 What it does not fix

The caption tells you what you are touching. It does not tell you the menu exists.

AUD-118 states the remaining problem in one clause: sub-1120px navigation is a single unlabelled orb with no first-run hint. Below the desktop rail's breakpoint, the site's entire navigation is one circular mark with a logo in it. A user who does not tap it never discovers that the site has sixteen destinations.

The audit's own suggestion — a transient "Menu" caption on first run — has not shipped. It is the single largest open item on this control, and Chapter 30 is direct about why it is hard to do well: a first-run hint that is too quiet is decoration, one that is too loud is an interstitial, and the platform already has enough first-run overlays that the audit had to suppress several to capture anything at all.

The caption solved recognition for people already inside the menu. Nothing yet solves discovery for people outside it.

Chapter Twenty-five

Blocking scroll without a scroll lock

The most valuable thing the deleted push-drawer left behind. Both standard techniques for locking background scroll clip the document to the visual viewport on iOS, which leaves a band of bare page background under Safari's floating bottom bar. The hub uses neither.

25.1 The two techniques, and what they do

The conventional options for stopping the page scrolling behind an overlay are body { overflow: hidden } and the position: fixed body technique (fix the body, offset it by the current scroll position, restore on close).

Both work. Both have the same side effect on mobile Safari, and it is not obvious from a desktop browser: they clip the document to the visual viewport. Safari's layout viewport extends behind its floating bottom bar, and the page normally scrolls under that bar — that is why content is visible through it. Clip the document to the visual viewport and the content that would have been under the bar is no longer rendered, leaving a strip of bare page background there.

On a dark page under a translucent bar that is a grey band across the bottom of the screen, appearing the instant a menu opens. It is not a rendering glitch that can be worked around from inside the overlay; it is a consequence of what the technique does to the document.

25.2 What the hub does instead

{{code:components/radial/radial.css|958-971|touch-action, not a scroll lock}}

Two mechanisms, one per input class.

Touch: touch-action: none on the overlay. The overlay covers the viewport, so a touch that would have panned the page starts on an element that declines to be panned. The document is never modified — it keeps its scroll position, its full height and its normal relationship to the browser's chrome. Content still flows under Safari's bottom bar exactly as it does when the menu is closed.

Pointer: a wheel listener on the overlay with { passive: false } calling preventDefault(), because touch-action governs touch and pen, not a mouse wheel.

Taps are unaffected — touch-action suppresses panning gestures, not clicks — so the scrim still dismisses on tap and the wedges still navigate.

25.3 The provenance, and why the comment is so long

This was established on a real device, for the mobile push-drawer, which blocked background scroll from its scrim for exactly this reason. That drawer no longer exists — commit 0969119 deleted it as unreachable code — so the finding survives only as comments, and it is deliberately duplicated in two places: the effect in RadialHub.tsx that installs the wheel guard, and the CSS rule that sets touch-action.

Duplicating a comment is normally a smell. Here it is insurance. Somebody optimising the stylesheet would see a lone touch-action: none and reasonably wonder why the component does not just lock the body like everything else does; somebody reading the component would see a wheel guard and wonder the same. Both need the answer, and the answer is a device-specific finding that cannot be re-derived by reading either file.

The transferable rule

An on-device finding that led you to reject the obvious implementation must be written down at the site of the unobvious one. Otherwise the next person will "simplify" it back, ship the regression, and rediscover the finding on a device they may not have.

25.4 What is deliberately not blocked

The page keeps its scroll position, which means the feed is exactly where it was when the menu closes. No restoration logic, no scroll-position bookkeeping, no jump — because nothing was ever moved. This is a real advantage of the technique beyond the iOS bug: the position: fixed body approach has to save and restore a scroll offset, and every implementation of that has an edge case around resize, orientation change, or a page that grew while the overlay was open.

Scrolling inside the overlay is also not blocked, because there is nothing inside it to scroll. The dial is sized to fit the viewport by construction — min(86vw, 70vh, 460px) — and the foot pill is a single row. A radial menu that needed to scroll would be a radial menu with too many destinations, and the answer to that is another deck, not a scrollbar.

Chapter Twenty-six

Safe areas and the floating stack

The single largest source of defects in the whole project, and the least glamorous. A fixed control at the bottom centre of every page has to coexist with a home indicator, a cookie banner, a mini player, a back-to-top button, a compose button, and the content scrolling underneath it.

26.1 The safe area

The site sets viewport-fit=cover, so the layout extends into the display's rounded corners and behind the home indicator. The body carries safe-area padding — and that padding does not apply to position: fixed elements, which position against the viewport rather than against the body's content box.

So every bottom-anchored fixed element in the module adds the inset itself:

--orb-bottom: calc(env(safe-area-inset-bottom, 0px) + var(--site-hub-orb-inset));

The orb, the aura, the foot pill and the feed's compose button all do this independently. Skipping it puts the control inside the home-indicator gesture strip, where taps are unreliable because the system claims them — and, visibly, makes it hang lower than the compose button beside it, which was always safe-area-aware. That mismatch is how the bug was noticed.

26.2 The floating-bottom stack

The orb is not the only thing that wants the bottom of the screen. The platform defines an explicit stack, and the orb is its bottom member:

{{fig:stack}}

Figure 26.1 — The floating-bottom stack. The orb carries data-floating="hub" and everything else lifts above it. Its footprint comes from --site-hub-orb-size and --site-hub-orb-inset, declared in globals.css precisely so that the stack's reserve and the orb's geometry cannot drift apart.

The coordination is done with :has() in globals.css: the presence of [data-floating="hub"] lifts the cookie bar, the mini player and the back-to-top control clear of it. The compose button shares the orb's row but is shorter, so it sits beside rather than above.

And the bug — AUD-102, the most-cited instance of AUD-003 — was that this entire mechanism was wrapped in @media (max-width: 767.98px). It ran on phones and never on anything wider. So at every viewport from 768 pixels up, on every page of the site, the orb sat on top of the cookie banner's text and its "Learn more" link. The fix was to extend the coordination to all widths.

Why a mobile-only media query was the wrong container

The reasoning that put it there is easy to reconstruct: floating controls pile up on phones, so coordinate them on phones. But the orb is fixed at every width — it is not a mobile control — and the cookie banner is full-width at every width. The collision was never about screen size. Scoping a coordination mechanism to the viewport where the problem was first noticed, rather than to the elements that actually participate, is a recurring shape of bug.

26.3 Clearance for content

Not colliding with other chrome is half the problem. The other half is that page content scrolls underneath the orb, and a 56-pixel disc floating over a feed covers text.

Two mechanisms, and they are different in kind.

Reserve at the end. --site-floating-reserve is derived from the orb's own size and inset tokens — not a guessed clamp — and every column that ends near the bottom of the page pads by it. Any full-height desktop panel stops --rad-corner-reserve short of the viewport bottom for the same reason. That solves the end of a scroll: the last feed card is not under the orb.

The legibility scrim. Nothing can stop text travelling through the orb's band mid-scroll. So the ground fades in behind it:

{{code:components/radial/radial.css|756-783|The legibility scrim under the docked orb}}

A radial gradient of the page background, 24rem wide, fading out by 78% of its radius, never hit-testable, and retracting the instant the dial opens because the overlay owns the screen then. Text passing beneath the orb dissolves into the page rather than colliding with a disc. It is the third of the audit's three prescribed fixes for AUD-003, and it is the one that turns an unavoidable overlap into a deliberate one.

26.4 The flexbox trap in the foot pill

AUD-504(b): the account pill's avatar disc painted over the settings gear beside it, at both viewports. The cause is one of the most common flexbox mistakes there is, and the fix is one line.

A flex item's default min-width is auto, which resolves to its content size. The identity pill contains an avatar and a display name; with a long name, its content size exceeded the space available, and because min-width: auto prevented it from shrinking below that, it kept its full width and overflowed onto its neighbour.

{{code:components/radial/radial.css|1332-1342|min-width: 0, and what ellipses}}

The fix is min-width: 0 on the pill, flex: none on the avatar so it is not what shrinks, and overflow: hidden plus text-overflow: ellipsis on the name so the name is what gives way. The icon buttons beside it also carry flex: none, so they can never be squeezed by the pill.

Worth stating as a rule, because it generalises well beyond this component: in any flex row that mixes a fixed element with a text element, the text element needs min-width: 0 and the fixed elements need flex: none. Without the first, nothing shrinks; without the second, the wrong thing does.

26.5 The last-resort guarantee

One more line, at the level of the shell:

.radial-shell { overflow-x: clip; }

Not hidden. clip. The distinction matters: overflow: hidden makes an element a scroll container, and a scroll container breaks position: sticky for its descendants — which would silently unstick the top bar and both rails. overflow-x: clip clips without creating a scroll container.

It is there as a guarantee of last resort: whatever else goes wrong inside the shell, nothing can scroll the document sideways. The module's overlap-safety section is explicit that this is a backstop rather than a strategy — the real work is grid tracks with minmax(0, …), min-width: 0 on every flex child, line clamps and overflow-wrap: anywhere on every slot that takes user content. Where overlap can be made structurally impossible, it is. This line catches what is left.
