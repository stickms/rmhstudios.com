Chapter Eighteen

Two layers, art and hit

The dial renders every sector twice: once as a decorative fill that the goo filter melts, and once as a real link that nothing filters. That duplication is the architectural answer to a hard constraint — the filter that makes the dial liquid destroys text.

18.1 The constraint

A goo filter works by blurring its input and then running the blurred alpha through a steep contrast ramp. The ramp is indiscriminate: it operates on alpha, and antialiased glyph edges are alpha. Run a 16-pixel-tall label through a blur and a ×19 alpha multiply and what comes out is not slightly softer text; it is chewed. Strokes fatten unevenly, counters fill in, and hinting is destroyed.

The module's README states the rule first among three: a goo group contains shapes only. Anything readable rides in a sibling layer above the filter.

18.2 The two layers

{{code:components/radial/radial.css|1054-1076|The split, and what the filter touches}}

The art layer is aria-hidden, pointer-events: none, and carries the bled polygon from Chapter 13. It contributes nothing but colour. The hit layer is the real navigation: sixteen anchors, each clipped to its exact sector, each containing its own icon and label.

Both are absolutely positioned over the same square with the same geometry, generated from the same wedges array in the same render. There is no synchronisation problem because there is nothing to synchronise: one array, two map calls.

18.3 The property this buys: colour correctness by construction

The split's obvious benefit is crisp glyphs. Its more valuable benefit is subtler, and it is the thing that finally solved the white-on-white problem in Chapter 20.

Because the glyph lives inside its sector's anchor, it inherits that anchor's color. And the anchor's colour is declared alongside its background:

{{code:components/radial/radial.css|1173-1199|Colour that tracks its own state}}

Read the chain. At rest the anchor is transparent with color: var(--site-text) — the page's ink, on a sector whose fill comes from the art layer beneath, which is a near-surface tint. On hover, focus or active the anchor fills with var(--site-accent) and its colour becomes var(--site-accent-fg) — that fill's paired foreground. The glyph follows automatically, because it inherits.

Both of those pairings are contrast-guaranteed by the platform: --site-text against --site-bg is the theme's fundamental contrast pair, and --site-accent-fg against --site-accent is checked at runtime by ensureReadableAccent(), which refuses to install a custom accent whose pair fails. So the glyph cannot be illegible in any theme, on any accent, in any state — not because someone tested it, but because there is no code path that produces an unpaired combination.

The glyph is correct because of where it lives, not because of what it was told.

18.4 The active state, on the art layer

One asymmetry: the current page's sector is filled on the art layer, not only on the hit layer.

.radial-hub__wedge-art.is-active { background: var(--site-accent); }

Both layers carry is-active, and the reason the art layer needs it is the filter. If only the unfiltered hit layer painted the active fill, the active sector's colour would sit crisply on top of a goo-melted neighbourhood — a hard-edged wedge in a liquid disc. Filling the art layer puts the active colour inside the filter, so the current destination melts into the dial like every other sector and simply happens to be the accent colour.

The active glyph's own ink still comes from the hit layer's color, unfiltered. Accent fill, liquid, filtered; contrast ink, crisp, on top.

18.5 Why not one layer with the filter on a pseudo-element

The obvious economy is a single set of anchors, each with a ::before carrying the filtered fill. It does not work, for a reason that is worth knowing because it recurs throughout this module: filter creates a new stacking context and a containing block for position: fixed descendants.

A filter on a pseudo-element of the anchor would be fine in isolation. But the goo effect requires the sectors to be filtered as a group — that is the entire mechanism; neighbouring shapes must be in the same filter region to fuse. Sixteen individually filtered pseudo-elements produce sixteen independently rounded sectors and no fusion at all. The filter has to be on a common ancestor, and a common ancestor of the anchors is also an ancestor of their glyphs.

Hence: two sibling groups, one filtered wholesale, one untouched. It is more DOM — thirty-two list items instead of sixteen — and it is the only arrangement that satisfies both constraints at once.

The same stacking-context hazard is why the orb's aura is a separate fixed layer rather than a pseudo-element on the orb: filtering the orb would filter the mark, and the mark is hairline line art that the alpha ramp would obliterate. And it is why the README's second rule reads never filter an ancestor of fixed chrome, with the note that nothing filters .radial-shell.

Chapter Nineteen

The metaball filter bank

Three SVG filters in one hidden <defs>, mounted once in the shell. Blur, then a steep ramp on alpha, then the sharp original composited back. Fifty-eight lines of component for the effect that gives the whole design language its name.

{{code:components/radial/LiquidGoo.tsx|29-58|The whole filter bank}}

19.1 How it works

Three primitives, in order.

feGaussianBlur spreads each shape's alpha outward. Two shapes that were near each other now have overlapping alpha halos, and in the region between them the summed alpha is higher than either halo alone.

feColorMatrix multiplies alpha by a large factor and subtracts a constant, which is a steep linear ramp clamped at both ends. Alpha above the threshold snaps to 1; below it, to 0. The blurred halo collapses back to a hard edge — but the position of that edge is now determined by the summed alpha, so the region between two nearby shapes, where alpha was boosted by both, is inside the new silhouette. A smooth neck. Metaballs.

feBlend composites the sharp original back over the fused result, so interior detail — borders, inner highlights — survives rather than being replaced by a flat silhouette.

The matrix row that does the work is the last one, and it is worth reading as arithmetic: 0 0 0 {ramp} -{(ramp-1)/2}. Output alpha is ramp × α − (ramp−1)/2. Set α = 0.5 and the output is ramp/2 − ramp/2 + 0.5 = 0.5. So the ramp is pivoted on α = 0.5, for any ramp value: half-alpha stays half-alpha, and everything either side is pushed to the extremes. That is what makes the three filters differ in aggressiveness but not in where they cut.

{{fig:ramp}}

Figure 19.1 — The three alpha ramps. All three pivot on α = 0.5; the difference is steepness, and therefore how far apart two shapes can be and still fuse. The blur radius sets the distance at which alpha is still non-negligible; the ramp sets how much of that halo survives.

19.4 The trap that is not in the code

The README's fourth rule is the longest in the module and describes a technique the code deliberately does not use. It is included here in full because it is the most transferable piece of knowledge the whole project produced.

There is a cheap, popular way to get a goo effect without an SVG filter: put an opaque plate behind some white blobs, apply blur() contrast() in CSS to threshold them, and add mix-blend-mode: difference to cancel the plate — black being difference's identity element. It works. It looks identical. And it is a landmine.

It stays invisible only while the compositor blends against the true page backdrop. The moment the layer gets its own render surface — which is a GPU-compositing decision, made by the browser, on criteria the author does not control — the plate stops cancelling and the entire box appears as a bright rectangle trailing the pointer. It does not reproduce under software rasterisation, so it is not a bug you can test your way out of.

The pointer metaball therefore uses an SVG alpha ramp — blur, then a steep curve on alpha alone — which emits the fused silhouette and transparency everywhere else. There is no box to reveal, on any path, and no blend mode at all, which also spares the per-frame backdrop readback that blending forces.

The general form of the lesson

An effect that depends on what a layer is composited against is an effect that depends on a decision the browser makes for performance reasons and can change between versions, between GPUs, and between one scroll position and the next. Alpha is a property of the layer. Blending is a property of the layer's relationship to its surroundings. Prefer alpha.

19.5 Cost, and the gate

An always-on SVG filter is continuous GPU work, so every decorative goo layer sits behind @media (min-width: 768px) and (prefers-reduced-motion: no-preference) — the same budget the ring backdrop already respects on phones. Below the gate the sectors render crisply, which is not a degraded dial so much as a different one: sharper, more legible, and arguably better on a small screen where the liquid character is mostly lost anyway.

The filter bank itself is always mounted — one hidden <svg width="0" height="0"> holding three <filter> definitions. Definitions cost nothing until referenced. Mounting it unconditionally means CSS can reference the filters from inside a media query without the component needing to know which queries matched, which keeps the gating entirely in the stylesheet where the rest of the degradation lives.

Chapter Twenty

White on white

Four commits, one recurring cause. The dial's icons were invisible, then the dial's sectors were invisible, then the logo mark was invisible. Every instance traces to the same idea: deriving contrast from the backdrop instead of from a token.

20.1 The idea that caused it

Sixteen sectors, any of which may be resting, hovered, focused or active, each with a different fill, on a dial that floats over an arbitrary blurred page in an arbitrary theme. What colour should a glyph be?

mix-blend-mode: difference is an extremely attractive answer. White, blended in difference mode, yields the exact inverse of whatever is beneath it. Maximum contrast, automatically, against any backdrop, in any theme, in any state, with no state tracking and no token plumbing. The glyph layer was made a single sibling above the filtered sectors and given difference blending, and it worked in the browser it was built in.

The failure is not about colour. It is about what "beneath" means. A blend mode composites against the backdrop within the element's own stacking context — not against whatever is visually behind it on screen. The glyph layer sat in a stacking context that did not contain the sectors it was meant to invert. So it inverted the context's own backdrop, which was nothing, which is to say it rendered white. On a white page, over a white-tinted dial. Commit 28e03b2: "radial menu icons were white-on-white."

The fourth is the interesting one, because it is the systemic fix. Rather than auditing every call site, globals.css now declares the pairings as :where() rules — zero specificity, so an element that sets only a background still gets the correct ink, and anything that states its own colour still wins. Since lucide icons paint with currentColor, one mechanism covers text and icons together.

20.3 What replaced the clever idea

The final architecture is the least clever available and the only one that is correct by construction. Stated as a rule:

Ink comes from the surface's paired token, and lives inside the surface

Do not compute contrast. Do not derive it from the backdrop. Name the foreground token that the theme author paired with the background you used, and put the text inside the element that carries that background so it inherits. Both halves matter: naming the token makes it theme-correct, and living inside the element makes it state-correct — hover, focus and active change the pair together, with no cross-layer coordination.

The comment left on the logo's colour declaration is the epitaph, and it names the exact mechanism so nobody re-derives the idea:

An earlier revision used mix-blend-mode: difference here; blending only composites against the backdrop inside the element's OWN stacking context, which is exactly how the hub glyphs ended up white-on-white. components/radial/radial.css — .radial-hub__logo

20.4 Why this class of bug is so easy to ship

Three properties make it uniquely dangerous, and they are worth recognising in the abstract.

It looks right in development. The default theme is the one the author has open, and the bug's whole character is that it depends on the resolved palette. An invisible control in a theme nobody opened is a control that ships.

It is invisible to type checking and to lint. Nothing is malformed. The CSS is valid, the tokens exist, the blend mode is supported. There is no rule that could have caught it short of rendering the page and looking at it.

The failure mode is total. An unreadable label is bad; an invisible one is a control that does not appear to exist. On the mobile dial, where sixteen glyphs are the entire navigation, a white-on-white glyph layer means the site has no navigation at all.

Which is why the platform's definition of done for a UI commit ends with the requirement that the change was actually looked at in the default, light and high-contrast themes, at a phone width and a desktop width, and once with reduced motion on. Three themes by two widths is stated as the floor. This family of four commits is why.

Chapter Twenty-one

Tokens, themes and the accent

The hub contains no colours. Every fill, edge, shadow and ink is an expression over custom properties that each theme redefines — including themes authored by users and bought with the platform's own currency.

Sixteen tokens, no hex values. The single number that looks like a colour anywhere in the hub's CSS is the orb's box-shadow, which uses rgba(0, 0, 0, 0.5) — a shadow, which is a darkness rather than a hue, and which the platform treats as a legitimate exception.

21.2 The color-mix discipline

Three of the hub's most important values are mixes rather than tokens, and each is doing something a token could not.

color-mix(--site-surface-opaque 94%, --site-text 6%) — the sector
"The solid surface, nudged toward the ink." Distinguishable from any page background in any theme, because every theme's ink contrasts with its own background by definition.
color-mix(--site-surface-opaque 86%, --site-text 14%) — the bed
The same expression at more than double the strength. The 8-point difference between them is the divider: the sectors sit on the bed and the bed shows through the gaps, so the dividers are a relationship between two mixes rather than a drawn line with a colour of its own.
color-mix(--site-text 55%, transparent) — the hairline
Firm enough to read as structure, soft enough not to become the loudest thing on the disc. Expressed as a transparency of the ink rather than as a grey, so it darkens on a dark theme and lightens on a light one along with everything else.

The pattern across all three: express a relationship, not a value. A designer picking hex values for these would need one set per theme, and would be wrong the first time a user authored a theme nobody anticipated.

21.3 The accent, and where it lands

The accent is the loudest decision in the hub: it is the orb's entire fill, and it is what a sector becomes when you point at it. On the default theme the accent is ink — a near-black — so the orb is a black disc with a white filigree mark, and hovering a sector fills it black with white glyphs. On the high-contrast theme the accent is yellow. On a user's purchased theme it is whatever they authored.

Fourteen curated accent presets ship, applied as inline overrides of the --site-accent* tokens on <html>, keeping everything else from the theme. Custom accents are allowed too — and this is where ensureReadableAccent() earns its place: it contrast-checks the accent against its foreground at runtime and refuses to install an unreadable pair. Without it, a user could give themselves a hub whose glyphs vanish, and the geometry would be flawless and the menu unusable.

A subtlety the audit found in a different component

On the default theme the accent is the ink, which means "accent" and "theme default" are visually identical — finding AUD-315 records that the settings page's accent swatches made "Ink" indistinguishable from "Theme default". The hub inherits the same coincidence harmlessly, but it is worth knowing when reading its CSS: on the shipped default, --site-accent and --site-text resolve to nearly the same colour, so several declarations that look like they must differ do not.

21.4 User themes

The platform lets members author and publish themes, and other users buy them with coins. A UserTheme is a set of colours plus a few scalar knobs, and themeCssVars() derives the full --site-* and --site-glass-* contract from them.

This is the strongest argument for the token discipline, and it is not hypothetical. The hub has to look deliberate in themes that did not exist when it was written, authored by people who have never read this document, and it does — because a theme cannot restyle the hub, it can only supply the contract the hub reads. Token maps from an older schema version are upcast on read rather than rejected, so a theme bought a year ago still resolves a complete contract today.

The corollary is a hard constraint on future work on this component: any new colour must be an expression over existing tokens, or a new token added to the contract and documented. A hex value in this file would be a hub that is subtly wrong in a theme somebody paid for.
