# RMH Vibes — how it works now

[`implementation.md`](./implementation.md)
is
the
original
2025
spec
(a
single
generated
HTML
file
in
an
iframe).
It
is
historical.
This
page
describes
what
the
code

Where

two
disagree,
the
code
and
this
page
win.
The
Discord
Activity
has

[`discord-activity.md`](./discord-activity.md).

A

and
TypeScript
project
written
by

model,
bundled
by
esbuild
on
the

and

as

The

is
`lib/rmhvibe/`,
`components/rmhvibe/`

`server/discord-bot/vibe.ts`.

## Ownership and remix

`lib/rmhvibe/ownership.ts`
decides
what
a
write
to
an
existing
slug
means
(`planVibeWrite`):

- No
  existing
  page:
  **create**.
- The
  signed-in
  user
  owns
  the
  page
  (`canEditVibe`):
  **edit**
  in
  place,
  which
  adds
  a
  version.
- Anyone
  else
  (signed
  out,
  another
  user,
  or
  an
  unowned
  legacy
  page):
  **remix**.
  The
  generator
  reserves
  a
  new
  page
  owned
  by
  the
  caller
  (slug
  is
  the
  source
  slug
  trimmed
  to
  26
  characters
  plus
  `-remix`,
  made
  unique),
  records
  the
  parent
  page
  and
  version,
  and
  never
  touches
  the
  source.
  A
  remix
  of
  "the
  page
  as
  it
  is
  now"
  records
  the
  latest
  version.

`fromVersionId`
branches
an
edit
or
remix
from
an
earlier
version,
replaying
that
version's
history
and
stored
project.
A
widget
stays
a
widget
on
edit
and
remix
(the
source
page's
`kind`
wins).

## Live build

`generateVibeStream`
(`lib/rmhvibe/vibe.server.ts`)
streams
`VibeStreamEvent`s
over
SSE
(`lib/rmhvibe/vibe-stream.ts`

raw-fetch
client):
`created`
(slug
reserved,

`thinking`,
`content`,
`preview`,
`done`,

While

previewer
parses

(`parsePartialProject`)

s

builds
it
with
`buildVibePreview`
(`vibe-bundle.server.ts`).
Imports
of
files
that
are
missing
or
still
being
written
resolve
to
a
generated
placeholder
component,
so
the
page
renders
whatever
is
ready
and
never
blanks.
A
`preview`
event
carries
the
bundled
`html`
plus
the
`done`
and
`pending`
file
lists.
Failed
preview
builds
are
dropped
silently.
Previews
end
with
each
attempt.
`VibeFrame`
crossfades
successive
documents
(160
ms)
and
`LiveBuildPanel`
shows
the
frame
beside
the
file

A
response
is
validated
before
it
is
saved.
If
it
is
not
a
working
app,
the
failure
is
fed
back
and
the
generator
retries,
up

3

surfaces

## Edit protocol

When
the
page
has
a
stored
project,
an
edit
sends
the
current
project
to
the
model
as
fenced
data
(`serializeVibeProject`)
with
`VIBE_EDIT_PROTOCOL`
appended.
The
model
answers
with
optional
`TITLE`,
`DESCRIPTION`,
`DEPS`
and
`TWEAKS`
lines,
`===FILES===`,
then
only
new
or
changed
files
in
full
(`--- file: path ---`)
and
`--- delete: path ---`
lines
with
no
body.
`applyVibeEdit`
(`lib/rmhvibe/vibe-project.ts`)
merges
that
onto
the
base:
listed
files
replace
wholesale,
deleted
files
go,
everything
else
is
kept.
An
omitted
`DEPS`
or
`TWEAKS`
line
keeps
the
base;
`TWEAKS: []`
removes
the
knobs.
It
returns
null
when
the
answer
has
no
marker
or
changes
nothing,
which
counts
as
a
failed
attempt.

Each
version
stores
its
`project`
(deps
and
files)
and
`tweakSpec`,
so
the
next
edit
starts
from
them.
A
legacy
page
with
no
stored
project
recovers
one
from
the
last
assistant
turn
in
its
history;
failing
that,
the
model
regenerates
the
whole
page.

**Truncation:**
if
the
provider
reports
`finish_reason: length`,
the
answer
is
never
materialized,
even
if
it
parses.
That
attempt
fails
with
"cut
off
at
the
output
limit
—
output
fewer
or
smaller
files"
and
the
retry
carries
that
reason
back.

## Host bridge: `window.RMHVibe`

A
vibe
frame
is
untrusted.
Its
sandbox
is
`allow-scripts allow-forms allow-modals allow-pointer-lock`
in
the
viewer
and
the
Activity
(`VIEWER_SANDBOX`)
and
just
`allow-scripts`
in
the
feed.
**Never
add
`allow-same-origin`.**
New
capabilities
reach
a
vibe
only
through
the
bridge.

- `lib/rmhvibe/bridge.ts`
  (client-safe,
  zod-free)
  is
  the
  protocol.
  Messages
  carry
  `__rmhvibe: 1`.
  `parseBridgeMessage`
  returns
  null
  for
  anything
  malformed;
  it
  validates
  every
  frame
  message
  and
  clamps
  what
  it
  keeps.
- `lib/rmhvibe/bridge-runtime.ts`
  is
  the
  script
  injected
  into
  the
  page
  that
  defines
  `window.RMHVibe`.
- `components/rmhvibe/useVibeBridge.ts`
  is
  the
  host
  side.
  It
  accepts
  a
  message
  only
  when
  `e.source`
  is
  the
  frame's
  `contentWindow`,
  replies
  with
  target
  origin
  `*`
  (the
  frame
  origin
  is
  opaque),
  allows
  at
  most
  50
  requests
  per
  second,
  and
  turns
  every
  failure
  into
  one
  of
  an
  allowlisted
  set
  of
  error
  codes
  (`unavailable`,
  `rate`,
  `invalid`,
  `forbidden`,
  `too-large`,
  `unauthorized`,
  `not-found`,
  `conflict`,
  `failed`).
  The
  frame
  never
  sees
  other
  error
  text.
- `components/rmhvibe/vibe-host-handlers.ts`
  maps
  `store.*`
  to
  the
  KV
  endpoint.
  The
  host
  kind
  is
  `viewer`,
  `feed`
  or
  `discord`.
  `room.*`
  is
  answered
  only
  by
  the
  Activity
  (`VibePlayer`);
  elsewhere
  it
  rejects
  as
  `unavailable`,
  so
  a
  vibe
  must
  keep
  working
  without
  the
  bridge.

The
API
as
the
model
is
told
it
(`VIBE_SYSTEM_PROMPT`):

- Always
  `await RMHVibe.ready`
  before
  first
  use
  and
  wrap
  calls
  in
  try/catch.
  Scope
  defaults
  to
  `'page'`
  (shared
  by
  everyone);
  `'user'`
  is
  per
  visitor
  and
  needs
  a
  signed-in
  viewer.
- `store.get(key, {scope}?)`
  returns
  the
  value
  or
  null.
  `store.set(key, value, {scope}?)`.
  `store.incr(key, by = 1, {scope, oncePerUser}?)`
  returns
  `{ value, counted }`.
  `store.list(prefix, {scope, order: 'key' | 'value-desc', limit}?)`
  returns
  `[{ key, value }]`
  (limit
  defaults
  to
  50).
- `room.send(data)`;
  `room.on(fn)`
  returns
  an
  unsubscribe
  function
  (not
  a
  Promise);
  `room.members()` returns `[{ name, avatarUrl, away, host, self }]` (`host` is the member who picked the vibe, `self` the viewer's own entry); `room.onMembers(fn)`.
- `room.send` is limited to 10 messages per second (the host rejects the excess with `rate`): throttle state updates and send only changes.
- Store calls are rate limited (a frame gets 10 `store.*` calls a second, and the endpoint's read bucket is 120 a minute): poll at most once every 2 seconds and prefer reacting to your own writes.
- `RMHVibe.visible` (boolean, true by default) and `RMHVibe.onVisibility(fn)` (returns an unsubscribe) follow the host's `visibility` event: pause audio and animation while hidden.
- `tweaks.get(key)`,
  `tweaks.all()`
  and
  `tweaks.on(fn)`
  are
  synchronous.
  Each
  knob
  also
  sets
  `--tweak-<key>`
  on
  the
  root
  element.
- Limits:
  key
  `/^[A-Za-z0-9:_.-]{1,64}$/`;
  a
  stored
  value
  is
  JSON
  of
  at
  most
  4096
  characters;
  `by`
  is
  an
  integer
  from
  -1000
  to
  1000;
  list
  `limit`
  at
  most
  100;
  a
  room
  message
  is
  JSON
  of
  at
  most
  2048
  characters.
  A
  call
  that
  breaks
  a
  limit
  rejects
  with
  an
  Error.

The
frame
can
also
send
events:
`ready`,
`error`
(message
at
most
500
characters),
`picked`
and
`pick:cancel`.
The
host
sends
`hello`,
`tweaks`,
`room:message`,
`room:members`,
`pick:start`,
`pick:stop`
and
`visibility`.

## KV store

`GET`
and
`POST /api/vibe/kv/$slug`
(`vibe-kv.contract.ts`,
`vibe-kv.server.ts`)
back
`RMHVibe.store`.
It
exists
only
for
a
ready
page.
The
server
enforces
every
limit;
the
frame
cannot.

| Rule           | Value                                                                                   |
| -------------- | --------------------------------------------------------------------------------------- |
| Scopes         | `page` (shared, owner `''`) and `user` (the signed-in viewer; signed out is 401)        |
| Key            | `/^[A-Za-z0-9:_.-]{1,64}$/`; the `__` prefix is reserved                                |
| Value          | JSON, at most 4096 characters                                                           |
| Keys per scope | 500 per page, 50 per user per page (409 when full)                                      |
| `incr`         | `by` an integer in [-1000, 1000]; `oncePerUser` needs sign-in and counts each user once |
| List           | `prefix` at most 64 characters, `limit` at most 100, order `key` or `value-desc`        |
| Writes         | 60 per minute per user, `maxBodyBytes` 16 KiB                                           |

Key-creating
writes
take
a
per-(page,
scope,
owner)
advisory
lock
so
the
key
count
cannot
race
past
its
limit.

## Deleted accounts and data export

When an account is erased (`anonymizeAccount`, `lib/account/deletion.server.ts`), the vibe pages it owned move to one shared
"Deleted user" account (`DELETED_USER_ID`, `lib/account/deleted-user.ts`) in the same transaction, and its per-user store rows
(`scope: 'user'`) are deleted. The sentinel row is created by the `deleted_user_owner` migration and is marked like every other
deletion tombstone (`banReason: account_deleted`, locked until 9999-12-31, no email, password, sessions or accounts), so search,
profiles and the owner chip treat it as "Deleted user" and nobody can sign in as it. Nobody's session is the sentinel, so
`canEditVibe` is false for everyone and other people remix the page. The sentinel itself is never anonymised.

"Download my data" (`/api/account/export`) includes a `vibes` section (`lib/rmhvibe/account-data.server.ts`): the pages the user
owns (slug, title, description, kind, prompt, status, timestamps, remix parent slug, tweak values, and the prompt of each version,
but not the HTML), their user-scope store rows, and the posts of theirs that embed a vibe. Each collection is capped at 10,000 rows.
